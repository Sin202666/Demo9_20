# 上线前审查

对全仓做 **性能 / 数据安全 / 本地化 / 玩法逻辑** 静态审查，输出一份总报告。  
**只读、不改代码**，除非用户明确要求按报告修复。

条款全文：[`docs/上线前审查标准.md`](../../../docs/上线前审查标准.md)。扫描时逐项对照 [checklist.md](checklist.md)。

**不要**走 `.cursor/skills/module-standard-review/` 的九类清单（注释、文件头、Utils 缓存、80 行拆分等本审查不看）。

## 输入

- 默认：**全仓四域一轮**，一份总报告。
- 用户若限定「只审数据安全」等单域，只跑该域，结论规则不变。
- 未指定排除时，按标准排除第三方与生成表风格。

## 流程

```
1. 读标准与 checklist → 2. 四域检索 → 3. 对命中点下追 2～3 层 → 4. 对照条款定级 → 5. 出报告
```

### Step 1：加载标准

审查前必须阅读：

- [`docs/上线前审查标准.md`](../../../docs/上线前审查标准.md) — 条款、级别、结论、排除
- [checklist.md](checklist.md) — 条款号速查
- 按需翻 [`docs/代码结构和设计开发规范.md`](../../../docs/代码结构和设计开发规范.md) §1.6 / §1.7 / §4 / §5 / §8
- 按需翻 [`docs/文本本地化开发规范.md`](../../../docs/文本本地化开发规范.md)

### Step 2：四域检索（一轮跑完）

在 `src/` 检索，再读命中文件。不要按 90 个模块逐个开规范性审查。

| 顺序 | 域 | 检索入口（见标准 §3） |
|------|----|----------------------|
| 1 | 性能 | Heartbeat / Stepped / `while true` / 热路径 `Instance.new` `GetChildren` |
| 2 | 数据安全 | `RegisterServerRemote*` / `ChangeStat` / DataStore / `ProcessReceipt` / `DEBUG_` |
| 3 | 本地化 | `SetText` / `TranslateByKey` / `.Text =` / `Language.luau` 的 `/e` |
| 4 | 玩法逻辑 | 从 `ChangeStat` / 入包 / 改货币 / 领取 / 购买 / 传送 / 技能结算 **往回追** |

排除：`SmartBone`；`GameAnalytics` 内部（只审项目接到 `ProcessReceipt` 的路径）；`Language.luau` / `ConfigInstance.luau` 的手写风格（仍须扫 `/e`、空 Key、重复 Key）。

### Step 3：定级

每条发现必须含：条款号（如 S5）、级别、`文件:行号`、现状、玩家或经济后果、修改建议（G5 只描述缺口，不指定满包策略）。

- 热路径（Heartbeat / 技能 tick / 命中）上的 `Instance.new` / `GetChildren` → **P1/P2 🔴**
- 打开 UI 时的同类调用 → **🟡**
- 调试 / GM Remote：**允许白名单**；无论是否 🔴，报告必须有 **「调试 / GM 口」专节** 点名每个 `DEBUG_*`（msgName、门禁、白名单、能改什么）
- 吃不准 → 「需人工」，禁止用风格问题凑数

### Step 4：结论（硬规则）

| 条件 | 结论 |
|------|------|
| 任一 🔴 | **不通过** |
| 无 🔴 | **有条件通过**（条件 = 未签字的需实测 + 须点名的白名单口 + 未关闭的 🟡 子系统） |

**Agent 本轮不得给出「通过」。** 无负责人在需实测清单上签字时，最高只能「有条件通过」。

## 报告模板

用中文。无问题的域写「✅ 未发现静态问题」+ 仍列出该域需实测项。

```markdown
# 上线前审查报告

## 概览

| 项目 | 内容 |
|------|------|
| 范围 | 全仓四域（或用户限定的域） |
| 排除 | SmartBone / GameAnalytics 内部 / … |
| 审查结论 | 不通过 / 有条件通过 |
| 问题统计 | 🔴 {n} · 🟡 {n} · 🟢 {n} · 需实测 {n} |

**最危险的 3 件事**（给制作人）
1. …
2. …
3. …

---

## 1. 性能
## 2. 数据安全
## 3. 本地化
## 4. 玩法逻辑

---

## 调试 / GM 口（S6，必填）

| msgName | 环境门禁 | 白名单 | 能改什么 | 级别 |
|---------|----------|--------|----------|------|
| … | Dev/Studio / 无 | 有 / 无 / 来源 | 背包/存档/邮件/… | 🔴 或「有门禁，须确认」 |

无此类口则写「未发现」，并说明检索范围。

---

## 阻断项（P0）

1. **[条款] 标题**（`file:line`）
   - 现状：
   - 后果：
   - 建议：

## 有条件通过必须关闭的项

- 需实测未签字：T1–T8（见下表）
- 白名单口须运营确认：…
- 其它 🟡：…

## 需实测清单

照抄标准 §8 表格，Agent 填「建议做法」列的具体入口（函数/界面名）；负责人 / 日期留空。

## 明确不在范围内

规范风格、数值平衡、第三方内部实现、…
```

## 行为约束

- **只读**：默认不改代码、不创建 commit、不手改 `Language.luau` / `ConfigInstance.luau`
- **基于证据**：每条指向代码位置；Studio 静态 UI（L8）标需人工，不得假装已扫
- **G5**：只指出满包 / 发奖失败谁成功谁失败、玩家少了什么；不规定必须回滚或进邮件
- 用户要求「审查并修复」时：先出完整报告，再按 🔴 → 🟡 修，修完简要对照条款
