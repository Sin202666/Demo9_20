# 模块规范性审查

对指定 Luau 模块，依据项目开发规范进行只读审查，返回结构化结果与可执行的修改意见。**不自动改代码**，除非用户明确要求修复。

## 输入

用户应提供以下之一：

- 模块文件路径（如 `src/ServerStorage/ServerSideCode/System/SystemBag.luau`）
- 模块目录路径（多文件 System，如 `SystemSave/`）
- 模块名（如 `SystemBag`）——需自行在 `src/` 下定位

若未指定范围，先询问；若指定整个目录，审查 `init.luau` 及同目录被 `require` 的子模块。

## 审查流程

```
1. 定位模块 → 2. 判定层级/类型 → 3. 读取源码 → 4. 对照清单审查 → 5. 输出报告
```

### Step 1：定位与范围

- 读取目标文件及同目录子模块（`require(script.*)` 引用）
- 记录：文件路径、总行数、**有效代码行数**、模块表名、是否为目录模块
- **有效代码行**：排除纯注释行（整行 `--`、`--[[ ]]` 块内各行）与空行；含代码的行（含行尾注释）计 1 行。500 行拆分阈值以此为准（结构 §3.7）

### Step 2：判定模块类型

根据物理路径确定适用规范子集：

| 路径模式 | 类型 | 重点审查 |
|----------|------|----------|
| `ServerSideCode/System/` | 服务端 System | 权威逻辑、存档、Remote 处理、服务端校验 |
| `ClientSideCode/SystemModule/` | 客户端 System | 无权威状态变更、连接清理 |
| `AllSideCode/ToolSystem/` | 业务工具 | 无服务端权威状态修改 |
| `AllSideCode/ToolBasic/` | 纯工具 | 无状态、无业务 |
| `AllSideCode/Class/` | 类模块 | `new`/`destroy`、生命周期 |
| `GuiScripts/` | UI | 不本地篡改权威数据；玩家可见文案走 `TranslationHelper` |
| `InitGame/Manager/`、`StarterPlayerScripts/Manager/` | Manager | 薄编排、无复杂业务 |
| `ReplicatedStorage/Msg/` | 通信实例 | 无业务脚本 |

### Step 3：加载规范

审查前**必须阅读**（按需选读章节，不必全文重复加载）：

- [`docs/代码结构和设计开发规范.md`](../../../docs/代码结构和设计开发规范.md) — 架构、模块设计、通信、数据、命名、编码、性能
- [`docs/代码注释和说明开发规范.md`](../../../docs/代码注释和说明开发规范.md) — 结构模板、注释
- [`docs/文本本地化开发规范.md`](../../../docs/文本本地化开发规范.md) — GuiScripts / 玩家可见文案（Key、入表、禁止手改生成表）
- [checklist.md](checklist.md) — 完整检查项（审查时逐项对照）

`.cursor/rules/roblox-agent-rules.mdc` 为精简版，与 docs 冲突时以 **docs 为准**。

### Step 4：逐项审查

按 [checklist.md](checklist.md) 九大类扫描，每条发现须包含：

- **严重程度**：🔴 必须修复 / 🟡 建议改进 / 🟢 可选优化
- **规范依据**：文档章节（如「结构规范 §3.3」）
- **位置**：`文件名:行号` 或函数名
- **现状**：简要描述违规或缺失
- **修改建议**：具体、可执行（含示例片段时只写关键 diff）

额外关注：

- 私有函数（`local function _*`）是否**全部**有块注释（System/ToolSystem/复杂模块为硬性要求）
- 文件头使用说明是否足够详细（功能、模块关系、示例；见注释 §2.1.1）
- 新建或本次改写文件头时，`Author` 是否等于 `git config user.name`（见注释 §2.1.0；违规一律 🔴）
- `@param` / `@return` 是否均为 `名称 类型 - 语义说明` 格式；`any`/`table` 是否补充字段或取值说明（注释 §2.3.1）
- `Init()` 内是否有版本迁移逻辑
- System 是否私自 `Connect` Remote
- 是否存在客户端权威结算（客上报发奖/伤害/击杀/掉落/任务完成被服照单记账）——结构 §1.6，一律 🔴 并严正警告
- 是否存在对同一实体位姿/速度/`WalkSpeed`/`Store.cframe` 的多源头抢写（无合成器/仲裁器）——结构 §1.7，一律 🔴 并严正警告
- 是否存在 `IsServer` / `RunService:IsServer()` 业务分支
- 函数内 `require`、绕过 `UtilsSystem` 的长路径 `require`、业务代码中未顶部缓存的 `Utils.X` 链式调用
- 超过 500 有效代码行（排除纯注释行与空行）、超过 80 行函数（标注并建议拆分点）
- 魔法数字/字符串、空 `pcall`、未断开连接
- 玩家可见文案是否走 `TranslationHelper.SetText` / `TranslateByKey`；Key 是否仅为字面量或配置表 `Zh*`；是否手改 `Language.luau`（本地化规范）

### Step 5：输出报告

使用下方模板，**用中文**输出。无问题的检查类写「✅ 通过」；有问题的类列出发现项。

## 结论判定

| 条件 | 结论 |
|------|------|
| 无 🔴，🟡 ≤ 3 | **通过** |
| 无 🔴，🟡 > 3 | **有条件通过** |
| 任一 🔴 | **不通过** |

架构分层错误、私自监听 Remote、业务模块 `IsServer` 混写、绕过 SystemSave 写 DataStore、Init 内版本迁移、**客户端权威结算**（结构 §1.6）、**多源头抢写位姿/速度**（结构 §1.7）、**新建/改写文件头时 `Author` 未对齐 `git config user.name`（或使用 Agent/Cursor/AI 等工具名）**、**手改 `Language.luau` / `ConfigInstance.luau`、玩家可见文案硬编码或 Key 非字面量/非 `Zh*`**（本地化规范） → 一律 🔴。

若用户拿「尚未二次审评通过的新方案」要求直接改业务代码：先按结构 **§1.8** 做开工门禁审评，**不通过则禁止开工**（与本 skill 默认只读审查一致）。

## 行为约束

- **只读审查**：默认不修改代码、不创建 commit
- **基于证据**：每条问题必须指向具体代码位置；不确定则标注「需人工确认」
- **避免误报**：简单 ToolBasic（<80 行、无状态）可省略文件头；缺分区注释（<80 行）可标注为可选优化；纯服务端无 UI 模块跳过本地化项；日志/注释中的中文不算玩家可见文案；在报告中说明放宽理由
- **子模块**：目录模块需分别审查子文件，在概览中汇总
- 用户要求「审查并修复」时：先输出报告，再按 P0→P1 顺序修复，修复后简要说明改动
